# Beat the Humanoid — browser prototype

Source: fujitamasahir/humanoid-spatial-memory@b50f81255756a9c8bd55dddd2ea72c54d58ebb7d. The 36-maze catalog and Python grid evaluator, memory, scheduling, navigation, observation and simulator are vendored unchanged. The demo pedestrian path generator is copied from engine.py. The browser adapter uses the original grid Sensor (radius 3, occlusion, zero noise), not MuJoCo rays, G1 footprint, independent emergency sensor or forward-first action planner. It blocks occupied-cell moves and counts a pedestrian entering the robot's previous cell as a contact. 2D-only, stylized SVG avatars, no physical collision claims. No FastAPI, WebSocket, backend or telemetry. Pyodide 0.27.7 and NumPy download via jsDelivr; computation in a browser Worker.

## Test locally
From the repository root: `python3 -m http.server 8000` and visit http://localhost:8000/games/beat-the-humanoid/ or the project page. Do not open via file://. Initial loading requires internet. Browser runtime has not yet been tested. The public portfolio branch is unchanged.

## Phase 2: experimental native physics mode

Choose **MUJOCO WASM · TEST** next to START CHALLENGE. The existing 2D mode remains the default. The official single-threaded MuJoCo JS 3.17.0 package is loaded from jsDelivr only for the native mode; it runs inside the existing worker alongside Pyodide. The pinned G1 XML is included; its 35 original mesh assets are fetched from the research commit on raw.githubusercontent.com and SHA-256 checked. No cloud simulation server is used. HTTPS or localhost is required for Web Crypto. The first native challenge downloads the runtime and model assets. An initialization ray self-test must pass before any native run. Errors do not silently switch the physics mode.

The adapter reuses the original MujocoNavigationScene, MujocoRayPerception, ObservedPedestrianTracker, independent 61-ray EmergencySafetyController and forward-first navigation policy. The Python compatibility layer mirrors the required NumPy shapes and forwards MuJoCo calls through the JS bindings. Contacts from evaluated poses determine the result; rejected actions are not contacts. The browser's layout validation still uses grid reachability (not the original footprint-based validation), the display remains 2D, and the G1 portraits remain temporary SVGs. The original evaluator's final rejected-action summary is patched in this browser copy to support tuple-valued sidestep/retreat records. Engine equivalence, collision accuracy, performance, and browser execution remain unverified. Compare fixed episodes with the original local engine before claiming parity. No changes to research or the deployed portfolio branch.

## Phase 4: 3D rendering from recorded MuJoCo poses

Select MUJOCO WASM · TEST and keep 3D VIEW checked. Three.js 0.178.0 is downloaded only when a 3D result is available. The physics worker copies the compiled visual mesh vertices and face indices into transferable buffers, exports measured geom transforms for each evaluated step, and sends them with ordinary results. No rendering code steps the world or changes the sensor, planner or collision result. Live playback and Review share a renderer and use the exact saved frame transforms; no simulated walking animation or interpolation is added. Wall boxes, obstacles and pedestrian capsules use the compiled geometry; colors, floor grid, camera and start/goal rings are presentation choices. Unchecking 3D VIEW uses the original 2D map with the same physics. If WebGL or the render-asset export fails, playback falls back to 2D (physics remains MuJoCo). Initial and result portraits still use temporary SVGs. The user confirmed the previous WASM version ran and matched the local game in their test; a comprehensive cross-engine benchmark remains outstanding. The Three.js renderer itself is not yet browser-tested.

## Phase 5: presentation animation

Character selection and result screens now use a separate Three.js renderer with the same pinned G1 geometry. The worker computes the original 60-frame Periodic backflip, Age ballet and Uncertainty boxing choreography and the original 54-frame kneel/bow/palm-IK defeat sequence (30 collapse + 24 repeating sob frames). The normal portrait bundle is prepared on page load; defeat poses are prepared only upon the first loss and cached for the page lifetime. The worker serializes portrait preparation and episode jobs; first-time asset or IK computation can delay a subsequent challenge. The 2D SVGs remain as fallback if WebGL or portrait generation fails. The winner returns to a bobbing standing portrait after the 3-second clip. For live/Review 3D frames, the original walking joint offsets are computed on a separate MjData using the original movement-phase formula; collisions, observations and routes use the unmodified evaluated pose, not the animated pose. The rendered character camera, lighting and material appearance approximate the local renderer; they are not pixel-identical. Actual browser animation/IK execution and numerical parity with walking presentation enabled are not yet verified.
